# Epic 6 詳細設計：店舗スタッフの予約運用

## 1. Story 6.1 予約状況と詳細の閲覧（Task 6.1.1〜6.1.3）

### 1.1 権限と導線

`/manage`から`/manage/reservations`へ進む。予約一覧・カレンダー・詳細はサーバー側で毎回`requireStoreAction("STORE_VIEW")`を通す。管理者と有効なスタッフは、操作権限の個別付与がなくても予約状況・履歴を閲覧できる。会員は閲覧できず、未ログインはスタッフログインへ転送する。閲覧用データ取得関数は`src/lib/manage/reservations.ts`に集約し、予約変更権限やクライアントから渡された会員IDを閲覧条件に使わない。画面は動的に描画し、個人情報を静的キャッシュに載せない。

### 1.2 Task 6.1.1：予約一覧と絞り込み

`date`は東京の暦日を初期値とし、`YYYY-MM-DD`の実在日付だけ受け付ける。`roomId`、`therapistId`はUUID、`status`は`CONFIRMED`、`IN_PROGRESS`、`COMPLETED`、`CANCELLED`だけを許可する。複数値や不正値はエラー表示にして、条件をリセットできる。`Reservation.businessDate`へ日付を指定し、任意の部屋・施術者・状態をAND条件で絞り込む。開始日時、予約IDの順に並べる。部屋・施術者候補には無効化済みも残し、古い予約を絞り込めるようにする。結果なしを明示し、一覧には取消済みも履歴として表示する。画面に表示する顧客・メニュー・担当・部屋は予約時点のスナップショットを使う。

### 1.3 Task 6.1.2：日別カレンダー

一覧と同じ絞り込み結果を使い、部屋別の縦軸時間表に表示する。各予約の`startsAt`〜`treatmentEndsAt`を青い施術領域、`treatmentEndsAt`〜`occupiesUntil`を黄色い占有領域として描き、詳細へリンクする。表示と時間計算は`Asia/Tokyo`で統一する。縦軸は表示対象の開始時刻と占有終了を含む時間帯に合わせる。取消済みは履歴一覧には残すが、解放済みの枠としてカレンダー上には描かない。`status=CANCELLED`のカレンダーでは占有枠なしを表示する。実際の施術超過による占有はこの予定表の範囲外である旨を明記する。

### 1.4 Task 6.1.3：予約詳細

`/manage/reservations/[id]`でUUIDを検査し、存在しない予約は404とする。予約番号、状態、施術・占有予定、顧客の予約時点の氏名・連絡先、会員ID、メニュー・オプションごとの予約時点の時間と料金、税込合計、担当施術者・部屋、備考、実績日時・取消情報を表示する。マスタや会員プロフィールの後日の変更で予約時点の内容を上書きしない。Story 6.2の変更操作はここでは追加しない。

### 1.5 検証

`npm run typecheck`、`npm run lint`、`npm test`（37件）は成功した。`npm run test:booking`も隔離PostgreSQLスキーマと実HTTPで成功し、スタッフ・管理者の閲覧、会員・未ログインの拒否、日付・部屋・施術者・状態の絞り込み、カレンダー、予約時点の料金・連絡先、取消済み履歴と占有除外、存在しない詳細の404を確認した。Next.jsの標準Turbopackビルドは実行環境のローカルポート制限で失敗したが、公式の`next build --webpack`で本番ビルドは成功し、両画面が動的描画対象であることを確認した。実ブラウザでのレイアウト・操作と本番環境での表示は別途確認が必要。

## 2. Story 6.2 店舗による予約操作（Task 6.2.1〜6.2.4）

### 2.1 Task 6.2.1：既存会員の選択と登録・変更

`/manage/reservations/new`は`RESERVATION_CREATE`権限者、`/manage/reservations/[id]/edit`は`RESERVATION_UPDATE`権限者に表示する。`GET /api/manage/members?query=`は`RESERVATION_CREATE`を毎回確認し、2〜100文字の氏名・メールアドレス・電話番号で検索して最大20件を返す。候補の状態と予約可否を表示し、`ACTIVE`、未削除、メール確認済みの既存会員だけを選択できる。非会員の仮登録や会員IDの自由入力は設けない。登録時は既存の`POST /api/reservations`へ会員ID、選択・表示済み合計、UUIDのリクエストキーを送り、保存トランザクションが会員状態、権限、マスタ、受付期間、必要枠を再検証する。

変更画面は予約の版、日時、メニュー、オプション、備考を初期表示し、保存前に空き時刻を検索する。`PATCH /api/reservations/[id]`へ期待版と新しいリクエストキーを送る。表示済み合計は変更検出にのみ使い、保存額は現行マスタから再計算する。保存失敗時は元の予約・オプション・枠をロールバックする。期限切れ、メニュー変更、枠競合、別画面での版更新を異なる案内で示し、再検索・再読込を促す。通信結果不明時は同じリクエストキーと内容で再試行する。

### 2.2 Task 6.2.2：部屋・担当施術者の変更

変更画面では自動割当のほか、両方の資源IDを明示して選べる。`GET /api/manage/availability`は`RESERVATION_UPDATE`権限、対象の確定予約、選択メニュー、資源IDを検証して候補を返す。店舗都合の受付期間外候補には`RESERVATION_EXCEPTION`権限も必要とする。空き判定では変更元予約だけを既存占有から除外し、選択した有効な部屋と施術者が営業日・休憩・全占有枠を通して使える時刻だけを返す。画面の候補を信用せず、既存の`lockBookingState`、会員・予約行ロックの下で`revalidateAtSave`に同じ資源条件を渡して再判定する。旧枠・オプションの削除、新しい予約本体・全枠・オプションの保存は単一トランザクションとし、競合時は旧割当を維持する。会員本人からの資源ID指定は403とする。

### 2.3 Task 6.2.3：取消と施術開始・完了

詳細画面には操作権限ごとに取消、開始、完了を表示する。取消は確認と任意の通常理由を経て既存の`DELETE /api/reservations/[id]`へ送る。通常期限を過ぎた店舗都合の変更・取消は`RESERVATION_EXCEPTION`権限と1〜1,000文字の理由を必須とし、既存監査行へ保存する。例外でも変更先の未来時刻、会員状態、営業・休憩・全枠の条件は省略しない。

`POST /api/manage/reservations/[id]/progress?step=start|complete`はそれぞれ`RESERVATION_START`、`RESERVATION_COMPLETE`を保存トランザクション内で確認する。`CONFIRMED→IN_PROGRESS→COMPLETED`だけを許可し、開始・完了実績はDB時刻を別項目に記録する。予約版を条件に更新し、監査行とリクエストキーで再送を冪等化する。開始・完了時に`ReservationSlot`を削除せず、早期完了でも予定占有終了まで枠を保持する。取消は確定予約に限り枠を解放する。

### 2.4 Task 6.2.4：競合と店舗運用の検証

`npm run test:booking`の隔離PostgreSQL・実HTTP検証に、管理画面と会員検索の権限、指定資源での2枠予約変更、同じ資源への競合失敗と元割当保持、会員本人の資源指定拒否、開始・完了の版と再送、完了後の枠保持、スタッフの変更／取消同時操作を追加する。担当変更後に旧施術者の無効化をプレビュー・確定し、移動済み予約に新しい要調整記録が作られないことを確認する。ローカル実ブラウザでのクリック操作、本番DB・本番環境での動作はこの統合テストの対象外。

## 3. Story 6.3 会員の状態管理と氏名一致審査（Task 6.3.1〜6.3.2）

### 3.1 Task 6.3.1：検索・状態表示・確認画面

`/manage/members`は管理者、または`MEMBER_FORCE_WITHDRAW`、`MEMBER_DELETE`、`MEMBER_RESTORE`のいずれかを持つスタッフに限定する。氏名・メール・電話番号の2〜100文字検索と状態絞り込みを提供し、更新順に最大50件を表示する。`/manage/members/[id]`では会員の状態・版、予約状態別の件数、退会時に取消される確定予約、会員状態の履歴を確認できる。検索結果と詳細は動的描画とし、会員・権限のないスタッフには表示しない。

操作ボタンは各権限で出し分ける。強制退会・論理削除では対象の確定予約件数と取消・枠解放を事前に示し、会員版と確定予約ID・版のダイジェストを送る。保存時にStory 4.3のトランザクションが再照合し、差異は409として再読み込みを促す。通信結果が不明な再送は同じ`requestKey`を使う。復旧は退会済みで初回有効化済みの会員にのみ提示し、理由を必須とする。復旧メールの発行後、本人がメール確認と新パスワード設定を完了するまで`RESTORE_PENDING`であり、過去の取消予約は復活しない。

`/manage/members/reviews`と`/manage/members/reviews/[id]`は管理者専用とし、保留中の申込者と氏名一致した退会会員の連絡先・状態・履歴への導線を表示する。管理者が理由を記入し、別人確認による入会許可か、同一人物としての却下を確定する。スタッフには審査画面・保存APIを開放しない。

### 3.2 Task 6.3.2：保存処理と整合性

退会・論理削除は既存の`POST /api/manage/members/[id]/withdraw`、復旧は`POST /api/manage/members/[id]/restore`に接続する。保存時に権限を再確認し、会員状態と版を検査する。退会時は`Member`を`WITHDRAWN/isDeleted=true`にし、未開始の`CONFIRMED`予約を取消して枠を解放する。予約・オプション・監査履歴は保持し、開始済み・完了済み予約の占有枠は残す。復旧は確認メール用トークンを発行し、本人の完了操作で`ACTIVE/isDeleted=false`に戻す。復旧中の再退会は古いトークンを無効化する。

新設の`POST /api/manage/members/reviews/[id]`は`MEMBER_REVIEW`という管理者専用アクションで認可する。入力は審査版、会員版、判断、1〜1,000文字の理由、UUIDリクエストキーに限定する。保存トランザクションでは予約系と同じ店舗状態ロックの後に会員・審査行を固定順でロックし、`PENDING_REVIEW`・未削除・メール確認済み・初回有効化前を再検証する。別人なら`ACTIVE`と初回有効化日時、同一人物なら`REJECTED`へ変更し、会員・審査の版と会員認証版を進める。審査結果・理由・管理者・日時を`MemberReview`に、判断を`AuditLog`に記録し、一致候補と退会者の履歴は保持する。同一キーの再送は元の結果を返し、異なる内容での再利用や古い版は409を返す。

### 3.3 検証

`npm run test:withdrawal`は隔離PostgreSQLスキーマと実HTTPで、管理画面の検索・詳細、管理者限定審査、スタッフの審査拒否、古い版の拒否、別人許可・同一人物却下・再送、元会員と予約履歴の保持を確認する。既存の同テストは強制退会・論理削除の権限、予約取消と枠解放、開始・完了済み履歴の保持、復旧メール発行と本人の完了、復旧中の再退会、競合を確認する。実ブラウザでのクリック操作、実メール受信、本番環境の動作は別途確認が必要。
