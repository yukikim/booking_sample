## 4. 予約受付・取消期限の設計

対応：Task 1.1.1。以下はREADMEの確定要件を具体化した検証例であり、実装・自動テストは未実施。

### 4.1 判定に必要な情報

| 入力 | 意味 |
| --- | --- |
| サーバー現在時刻 | クライアントから送られた現在時刻は使用しない |
| 予約対象日 | Asia/Tokyoでの営業日 |
| 営業設定 | 各基準日に有効な営業時間・休業日。保存済みの将来設定も対象 |
| 操作種別 | 通常予約、通常取消、店舗都合の変更・取消、退会による自動取消 |
| 操作者・対象予約 | 本人・操作権限・会員状態・予約状態の検証に使用 |

### 4.2 共通規則

- 受付開始：予約対象日から暦日で30日引いた日の00:00（Asia/Tokyo）。
- 受付締切：予約対象日の前の暦日の、設定上の営業終了時刻。前日が休業日でも日付を繰り上げない。
- 取消締切：予約対象日より前の直近営業日の営業終了時刻。
- 受付開始・締切は境界時刻を含む。締切を超えた時点で通常操作を拒否する。
- 当日予約は受け付けない。通常操作では管理者・スタッフにも同じ期限を適用する。
- 日付計算・設定参照はAsia/Tokyoで行う。予約等の時点はDBで`timestamptz`として保持する。
- 検索結果は枠の確保ではない。保存時に現在時刻・設定・会員状態・空きを再検証する。
- 期限内であることだけでは予約成立を意味しない。休業日、休憩、資源の空き、認証等の条件も必要。

### 4.3 境界の検証例

基準：予約日は2026-10-16、営業時間は09:00〜18:00。特記がなければ前日まで営業日、会員・空き・権限等の他条件は満たす。表の時刻はすべてAsia/Tokyo。

| TIME-02 | 09-16 00:00:00に予約 | 30日前00:00のため期限判定は許可 |
| TIME-03 | 10-15 17:59:59に予約 | 締切前のため期限判定は許可 |

### 4.4 例外と予約状態

| 操作 | 必須条件 | 結果 |
| --- | --- | --- |
| 店舗都合の期限後変更・取消 | 操作権限と理由記録。変更先の設定・空き・会員状態等も検証 | 通常期限後も実行可能。変更失敗時は元の予約・占有を維持 |
| 退会・削除時の未開始予約 | 退会処理の認可と対象状態の検証 | 通常取消期限後でも取消し、占有枠を解放 |
| 退会時の施術中予約 | 施術中状態を確認 | 予約と占有枠を維持。早期完了でも元の占有終了までは短縮しない |
| 復旧 | 復旧確認メールの確認完了 | 会員を有効化。取消済み予約は復活させない |

店舗都合の例外は一般利用者の締切回避に使用できない。設定変更・退会との同時操作の制御はTask 4.2.3、4.3.3で実装・統合テストする。

## 8. 営業日・営業時間・休憩の適用日付き設定

対応：Task 1.1.2。2026-09-17の継続指示を受け、本章の方針を採用しREADME第11章へ反映した。設計Taskは完了、実装・DB統合テストは未実施。以下の「案」「提案」は設計時の表現であり、物理的な実装方式を除き採用した方針を指す。物理スキーマはTask 2.2.6、実装はStory 3.2で具体化する。

### 8.1 ハンズオンで確認する例

9月16日に「10月17日から閉店を18:00から17:00へ変更」と保存する。

1. 適用日との差は31日なので通常の事前変更になる。
2. 保存直後でも、10月17日の検索には新しい17:00閉店を使う。
3. 10月16日の検索には従来の18:00閉店を使う。
4. 10月17日17:00〜18:00の既存予約があれば、保存時点で要調整にする。予約と占有枠を残す。
5. 店舗が確認して送信操作を行うまで案内メールは送らない。

重要なのは「今有効な設定」と「予約対象日に有効な設定」の違い。10月17日00:00に設定を書き換える定期処理は用意せず、対象日から参照する履歴を選ぶ。

### 8.2 確定要件と今回の設計案

**READMEで確定していること**

- 適用日はAsia/Tokyoの00:00を境界とする。31日後以降は通常、30日後までは直近変更。
- 将来日も対象日に有効な設定で判定する。再変更時には保存日から日数を計算し直す。
- 保存時に既存予約への影響を確認する。影響予約と占有枠を維持し、確認後に案内する。
- 部屋・施術者の無効化には適用日ルールを追加しない。ただし影響確認は共通化する。

**未決定だった細部への提案**

| 項目 | 設計案 | 理由 |
| --- | --- | --- |
| 営業時間 | 曜日別の基本設定＋特定日だけの上書き | 通常営業と祝日・臨時休業を区別できる |
| 時刻 | 開閉店・休憩開始は正時のみ。開店＜閉店、同日内、翌日またぎ不可。閉店は最大23:00 | 全予約を共通の1時間枠へ揃える。24:00対応は今回含めない |
| 休憩 | 施術者・曜日ごとに開始時刻と60分後の終了を保持。未設定も明示的に保持 | 未設定なら割当不可とする要件を判定できる |
| 休業日 | 閉店時刻を必須として保持。休業へ変更する際は変更前の有効な閉店時刻を初期表示し、明示保存する | 受付締切を計算できるようにする |
| 過去・当日適用 | 通常の設定履歴では拒否し、最短は翌日。初期データだけ運用開始日から有効な基準設定を作る | 当日の00:00へ遡って設定を変更する曖昧さを避ける |
| 当日の緊急対応 | 部屋・施術者無効化、理由付きの店舗都合変更・取消で対応。臨時休業の即時反映が必要なら別途要件化 | 通常の適用日履歴と即時対応を区別する |
| 同一適用日 | 別の設定を二重作成せず、版を指定して訂正。旧版は履歴に残す | 更新の上書きを検出し、変更前後を追跡できる |
| 予定取消 | 適用日前のみ可能。物理削除せず取消履歴を残し、取消後の設定で影響を再確認 | 予定を取り消すことで営業時間・休憩が再度変わるため |

当日適用不可と時刻の制限は2026-09-17に採用し、READMEにも反映した。

| 曜日別営業設定 | 適用日、7曜日すべての営業／休業・開閉店時刻 | 適用日ごとに現行の版を1つ。全曜日を含むスナップショット |
| 日別営業上書き | 対象営業日、営業／休業・開閉店時刻 | 対象日ごとに現行の版を1つ。対象営業日＝適用日で、その日だけ有効 |
| 曜日別休憩設定 | 施術者ID、適用日、7曜日の休憩または未設定 | 施術者＋適用日ごとに現行の版を1つ。全曜日のスナップショット |
| 設定変更履歴 | 変更ID、対象、操作種別、旧版・新版、操作者、保存日時、理由 | 追加・訂正・取消を記録し、過去の内容は保持 |
| 設定管理情報 | 店舗全体の設定版番号 | 設定の更新・取消ごとに増加。古い編集画面の送信を検出 |
| 影響記録 | 変更ID、予約ID、影響理由、対応状態、送信要求との関連 | 同一変更＋同一予約の重複登録を防止。配信状態と対応状態は分離 |

初期設定は09:00〜18:00を基本とし、営業曜日・休業曜日と各施術者の休憩は初期データ作成時に設定する。営業曜日はREADMEで未指定なので、全曜日営業を確定仕様にしない。

将来設定は独立したスナップショットとして保存する。途中の設定を訂正・取消しても、それより後の保存済みスナップショットへ内容を自動転記しない。管理画面で後続設定の存在と内容を表示する。

### 8.4 対象日の設定を取得する手順

1. 対象日をAsia/Tokyoの暦日として扱う。
2. 営業設定は、その日の有効な日別上書きがあれば優先する。
3. 日別上書きがなければ、取消済み・旧版を除き「適用日≦対象日」のうち適用日が最も新しい曜日別営業設定を選ぶ。その日の曜日の値を使う。
4. 休憩は施術者ごとに同じ条件で履歴を選び、その日の曜日を参照する。未設定の場合は割り当てない。
5. 営業設定が存在しない場合は、暗黙に09:00〜18:00へ補完せず設定不足として新規受付を停止する。

予約受付締切は前の暦日、取消締切は前の直近営業日について、この営業設定の取得処理を使う。直近営業日が基準設定の開始日までに見つからなければ、締切算出不可として通常操作を拒否し店舗へ案内する。無制限に過去を探索しない。

曜日別設定の影響範囲は、適用日から次の有効な曜日別設定の適用日前日まで。日別上書きが優先される日はその内容を使う。日別上書き自体の変更は対象日のみが範囲になる。休憩も対象施術者の次の履歴までを範囲とする。

### 8.5 保存・訂正・取消の処理

1. サーバーで操作権限、適用日、時間、対象、編集元の設定版番号を検証する。
2. 保存日のAsia/Tokyoの暦日を用いて日数差を計算し、通常／直近変更を区別する。画面で確認後に日付が変わった場合も再計算する。
3. 変更前後の設定を仮に組み立て、既存予約に対する影響と締切変更を画面に表示する。この時点では保存・枠解放・送信をしない。
4. 確定時には競合制御下で版番号と予約を再取得し、影響を再計算する。確認時と影響対象・理由が変わった場合は再確認を求める。
5. 設定の新版または取消、変更履歴、設定版番号、影響記録を同一トランザクションで保存する。途中失敗時はすべて取り消す。
6. 新規検索は保存後の設定を使う。影響がある予約は要調整として表示し、予約本体・割当先・占有枠を勝手に移動・削除しない。
7. スタッフの送信操作で初めて案内の送信要求を作る。変更ID＋予約ID＋通知種別で要求の二重登録を防ぐ。

影響確認では、休業、施術終了・占有終了の閉店超過、開始時刻の範囲外、休憩との重複・休憩未設定を調べる。締切変更だけの場合も変更前後の期限を表示・記録するが、施術可能な予約を自動取消・要調整にはしない、という案とする。

締切の影響は予約日だけでは判定できない。安全性を優先する初期実装では、将来の有効予約全件を対象に、予約日・受付締切基準日・取消締切基準日の設定を変更前後で比較する。予約受付期間の30日だけに走査を限定しない。

### 8.6 同時操作と上書きの防止

初期の小規模・単店舗構成では、予約と設定の整合性に関わる更新を、同じ店舗単位の排他制御に参加させる案とする。物理的なロック方式・取得順序・再試行条件はTask 2.2／4.2で確定し、DB統合テストで検証する。

- 設定保存・訂正・予定取消だけでなく、予約作成・変更・取消、資源無効化、退会による予約取消も同じ排他制御を使う。
- ロック取得後に設定・会員状態・予約の最新値を読み直す。検索時点の値で保存しない。
- 予約保存が先に確定すれば、後続の設定変更はその予約を影響確認の対象に含める。
- 設定変更が先に確定すれば、後続の予約保存は新設定で再検証する。
- 古い設定版番号の編集要求は競合として拒否し、最新版の再読込を案内する。後勝ちで上書きしない。
- 排他制御はDBの部屋・施術者別枠一意制約を置き換えない。両方を使用する。
- SMTP通信と利用者の確認待ちはトランザクション外で行い、ロックを保持しない。

単店舗全体の直列化は実装を簡潔にする一方、同時更新数が増えると待ち時間が生じる。実測後にロック範囲を細分化する場合も、上記の整合性を維持する。

### 8.7 予定取消と影響予約の再評価

- 取消対象は適用日が保存日より後の設定。適用日当日以降は履歴取消を拒否し、翌日以降の新しい設定で修正する。
- 同一適用日の訂正後に予定取消した場合、その適用日の予定全体を無効にする。訂正前の旧版を自動復活させない。
- 曜日別設定を取り消すと直前の有効設定を使い、後続の予定は維持する。日別上書きを取り消すと曜日別設定へ戻る。
- 取消で営業時間が短くなったり休憩が変わったりする可能性があるため、通常保存と同じ影響確認を行う。
- 以前の影響が解消しても予約と枠は維持する。影響記録を消さず「影響解消・店舗確認待ち」として表示し、店舗の確認後に対応を閉じる案とする。別の未解消理由があれば要調整を残す。
- 古い設定に基づく未送信の案内要求は送信対象から外し、理由を記録する。送信直前にも設定版・予約版を再検証する。送信中または送信済みは取り消せないため、店舗へ追加連絡の必要性を表示する。
- 変更済み・取消済みの予約を予定取消によって復活・再変更しない。

## 9. 日時・料金・会員入力の型と検証

対応：Task 1.1.3。READMEと第8章の採用事項を具体化する。2026-09-17の継続指示を受け、最大長・数値上限・入力整形を含め採用しREADMEへ反映した。以下の「提案」「案」は設計時の記述であり、明記した後続Taskの未決定事項を除き採用済み。実装・自動テストは未実施。

### 9.1 ハンズオン：1件の予約をデータに分ける

例：2026-10-17の10:00から、ボディケア60分・6,000円とヘッドマッサージ10分・1,000円を予約する。

| 内容 | 値 | 扱い |
| --- | --- | --- |
| 予約日 | `2026-10-17` | 店舗の暦日 |
| 開始時刻 | `10:00` | 店舗時刻。日付と組み合わせるまで時点ではない |
| 予約開始の時点 | `2026-10-17T01:00:00.000Z` | Asia/Tokyoの10:00に対応するUTC時点 |
| 合計時間 | 70分 | 整数。メニューとオプションからサーバー計算 |
| 必要枠 | 2枠 | 70÷60を切り上げ |
| 施術終了 | 11:10 | 分単位。正時には丸めない |
| 占有終了 | 12:00 | 枠単位で計算 |
| 合計料金 | 7,000円（税込） | 円単位の整数。税込料金を加算し、再度税を加えない |

画面が送るのは予約日・開始時刻・メニューID・オプションID等。合計料金・時間・終了時刻は表示用に計算しても、保存値として信用せずサーバーで再計算する。

### 9.2 日付・時刻・時点の型

以下は論理型とDB型の設計。具体的な変換ライブラリ・Prisma宣言は実装Taskで確定する。

| 対象 | 入出力 | DBでの保持 | 検証 |
| --- | --- | --- | --- |
| 営業日・適用日 | `YYYY-MM-DD`文字列 | `date` | 書式と実在日を検証。`2026-02-30`等を拒否 |
| 開閉店・休憩時刻 | `HH:mm`文字列 | タイムゾーンを持たない`time` | 正時、00:00〜23:00。同日内、開始＜終了、休憩は60分 |
| 予約開始候補 | `HH:mm`文字列 | 予約開始の時点へ変換 | 対象日の開店以上・閉店未満、正時、受付・占有条件も検証 |
| 予約開始・施術終了・占有終了 | UTCのISO 8601文字列（応答） | `timestamptz` | 日付と時刻をAsia/Tokyoで解釈。終了はサーバー計算 |
| 登録・更新・施術開始・完了日時 | UTCの時点 | `timestamptz` | サーバー側で取得。クライアント指定値を採用しない |
| 曜日 | 整数0〜6（日〜土） | 整数 | 店舗の日付から判定。範囲外・小数を拒否 |

- 日付だけの値をブラウザやサーバーのローカルタイムゾーン任せで日時に変換しない。
- 30日前や適用日差は暦日で計算する。UTCの日時を切り出して店舗の日付にしない。
- 正時制限は予約開始・設定時刻の制約であり、施術終了を正時へ丸める制約ではない。
- 占有と休憩は開始を含み終了を含まない区間として比較する。10:00〜11:00の占有と11:00〜12:00の休憩は重複しない。
- 時点はミリ秒精度に統一する案とし、締切18:00:00.000は許可、18:00:00.001は拒否する。
- 表示はREADMEどおり`Intl.DateTimeFormat`の`timeZone: "Asia/Tokyo"`、`hourCycle: "h23"`と`formatToParts()`を用い、`2026年10月17日10:00`へ統一する。

### 9.3 時間・料金の入力

円・分・枠数は整数で扱う。以下の上限は初期実装に向けた提案であり、READMEで指定された価格や時間を固定するものではない。

| 項目 | 型・提案範囲 | 補足 |
| --- | --- | --- |
| メニュー時間 | 整数、1〜1,380分 | 00:00〜23:00の最大営業幅まで。実際の予約可否は営業時間・休憩で別途判定 |
| オプション追加時間 | 整数、0〜1,380分 | 0分を有効値として扱う |
| メニュー・オプション料金 | 整数、0〜1,000,000円（税込） | 無料項目も許容する案。負数・小数は拒否 |
| 合計時間 | 整数、1〜1,380分 | 加算後にも範囲を検証。超過なら受付不可 |
| 合計料金 | 整数、0〜1,000,000円 | 個別が範囲内でも合計超過は拒否 |
| 必要枠数 | 整数、合計時間÷60の切り上げ | 利用者に入力させない |

管理画面の数値入力は、空欄を0に変換しない。フォームからの文字列は前後空白を除いた後、半角数字のみの表現を整数に変換する案とする。`6,000`、`1e3`、`10.5`、負号付きは入力エラーとし、入力例を提示する。JSONで数値を受ける場合も整数・範囲を検証する。

オプションIDは配列として受け、同一IDの重複を拒否する。存在しないID・無効な項目を拒否し、DBの最新の名称・時間・税込料金から計算する。表示後に料金・時間が変わった場合は、新しい内容を再確認してから保存する設計とする。

### 9.4 入会入力の型と検証

必須項目と電話・郵便番号の桁数、年代、パスワード最小長はREADMEの確定要件。その他の文字数上限・整形は今回の提案。

| 項目 | 保存・処理する型 | 検証・整形案 |
| --- | --- | --- |
| メールアドレス | 文字列、必須 | 前後空白除去、最大254文字、内部空白・改行を拒否、メール形式を検証。実際の利用確認は確認メールで行う |
| 姓・名 | 別々の文字列、各必須 | 前後空白除去後、各1〜100文字。改行・制御文字を拒否。漢字・カナだけに制限せず内部の空白やハイフン等を保持 |
| 電話番号 | 文字列、必須 | 前後空白・ASCIIハイフンを除去後、半角数字10〜11桁。先頭0を保持 |
| 郵便番号 | 文字列、必須 | 前後空白・ASCIIハイフンを除去後、半角数字7桁。先頭0を保持 |
| 年代 | 整数の限定値、必須 | `20 / 30 / 40 / 50 / 60 / 70 / 80`のみ。実年齢・生年月日とは扱わない |
| パスワード | 入力時のみ文字列 | 15〜128文字を提案。Unicodeコードポイント数で数え、空白除去・正規化・切り捨てをしない。数字・記号の混在は強制しない |

電話番号・郵便番号は数値型の入力を受け付けない。全角数字・内部空白・全角ハイフン等を黙って変換せず、半角数字での入力を案内する案とする。これは桁数・文字種の検証であり、実在する番号の確認を意味しない。

一般文字列の最大長もUnicodeコードポイント数で数える案とし、画面とサーバーで同じ規則を使用する。メールの国際化対応範囲・大文字小文字・重複判定用の正規化、氏名照合用の正規化はTask 1.2.2で確定する。表示用氏名を照合の都合で置き換えない。

パスワードは平文でDB保存・ログ出力しない。ハッシュ方式と128文字まで切り捨てず処理できる構成はStory 1.2で確定する。入力検証を満たしても、メール未確認・重複・退会済み等では入会完了にならない。

### 9.5 予約入力とサーバー側の責務

| 入力 | 検証・扱い |
| --- | --- |
| 予約日・開始時刻 | 書式、実在日、正時、対象日の設定、受付期限、全占有区間の空きを検証 |
| メニューID | 必須、存在・有効状態をサーバーで確認 |
| オプションID配列 | 任意、省略時は空配列。重複・存在・有効状態を確認 |
| 備考 | 任意、最大1,000文字を提案。改行を保持し、HTMLとして解釈しない。空欄は未入力として扱う |
| 会員ID | 本人予約では入力として受け付けずセッションから取得。代理予約は対象会員の状態と操作権限を確認 |
| 部屋・施術者・料金・終了時刻 | 本人予約ではサーバーで割当・計算。管理操作での指定は別途権限と空きの検証を行う |

入力は操作ごとの許可項目だけを受け付け、会員状態・権限・削除フラグ等を登録フォームから保存できないようにする。型チェックだけで本人確認・認可を代用しない。

### 9.6 エラー時の画面と保存

1. 画面側で入力ミスを早期表示し、サーバー側でも同じ規則で再検証する。
2. 必須・書式・範囲のエラーは項目の近くに具体的に表示する（例：「電話番号は半角数字10〜11桁で入力してください」）。
3. エラーがあれば保存を行わず、修正可能な入力を保持する。パスワードを応答・ログへ含めない。
4. 空きの消失・設定や料金の変更は項目の書式エラーと分け、再選択・再確認へ案内する。
5. 登録有無に関わるメール案内はREADMEの共通文言「対象のアドレスに案内を送信します」を使う。重複照合の内部理由をそのまま表示しない。

### 11.1 ハンズオン：閲覧できても取消できない

5. 権限を解除すると、ログイン済みのAも以後の取消操作を拒否される。

「誰か」と「何をしてよいか」を分ける。管理者にも通常の予約期限・空き・会員状態の検証は適用する。

### 11.3 認証主体とログイン入口

Credentialsの入口を会員・スタッフ・管理者の3種類に分ける案とする。入口の選択自体は権限の証明にならず、各入口が対応する資格情報をサーバーで検証する。

| 主体 | ログイン画面案 | 照合先 | 成功条件 |
| --- | --- | --- | --- |
| 会員 | `/login` | Memberのメール・パスワードハッシュ | メール確認済み・有効・未退会、資格情報一致 |
| スタッフ | `/staff/login` | StaffAccountのメール・パスワードハッシュ | 有効なスタッフ、資格情報一致 |
| 管理者 | `/admin/login` | サーバー環境変数の管理者メール・パスワード | 環境変数が設定済みで資格情報一致、管理者の有効状態を確認 |

- 主体は`MEMBER`・`STAFF`・`ADMIN`とIDの組で区別する。会員と店舗利用者をメール一致だけで統合しない。
- 会員登録からStaffAccountや管理者区分を作らない。スタッフ作成時も主体は必ずSTAFFで、権限は空から開始する。
- 管理者の監査用IDは固定の管理者レコードに対応させる案とする。資格情報はREADMEどおり環境変数で管理し、そのパスワードをDBへ複写しない。DBの区分変更だけでスタッフを管理者ログイン可能にしない。
- 管理者用の環境変数案は`ADMIN_EMAIL`・`ADMIN_PASSWORD`・`ADMIN_AUTH_VERSION`。NextAuth用の秘密鍵は`AUTH_SECRET`。いずれもサーバー専用とし、値を設計書・ログ・クライアントへ出さない。
- 管理者資格情報変更時は認証版も更新し、全稼働インスタンスへ反映する。反映途中の旧インスタンスを残したまま失効完了と扱わない。
- 同一ブラウザでは認証セッションを1つとし、別主体への切替はログアウト後に行う案。同時利用は別ブラウザプロファイルを使用する。
- ログイン失敗は存在しないメール・パスワード不一致・利用不可を区別して外部へ表示しない。レート制限とハッシュ方式はTask 1.2.2で具体化する。

### 11.4 セッションと失効

NextAuthの`jwt`戦略を明示し、Prisma Adapterによるユーザー自動保存には依存しない案。アプリDBに失効確認用のセッション記録を持つが、これはNextAuthの`database`戦略とは別物。

| データ | 内容 |
| --- | --- |
| JWT | 主体種別・主体ID、ランダムなセッションID、認証版。パスワード・個人情報・権限一覧を格納しない |
| アプリのセッション記録 | セッションID、主体、作成・絶対有効期限・失効日時、発行時認証版 |
| 主体の認証版 | パスワード再設定・退会・無効化時に増加させ、過去セッションを拒否するための値 |
| ブラウザへ返す情報 | 表示に必要な主体・最小限の表示情報。Cookie値・認証秘密・ハッシュは返さない |

期限は会員7日、スタッフ・管理者8時間の絶対期限を提案する。JWTの更新があってもDB記録の絶対期限は延長せず、到達したら再ログインを求める。ログイン成功時に新しいセッションIDを発行し、発行途中で失敗した記録は有効期限後に掃除する。

各保護処理で、JWT検証に加えてセッション記録の存在・主体一致・期限・失効、主体の有効状態と認証版を確認する。DB障害時は許可せず一時的な利用不可として扱う。結果を利用者間で共有するキャッシュへ保存しない。

ログアウトでは現在のDBセッションを失効させてからCookieを削除する。失効が失敗した場合は、サーバー側失効まで成功したと表示しない。退会・パスワード再設定・スタッフ無効化では認証版更新と状態変更を同じトランザクションに含める。復旧後も古いセッションは復活させない。

本番CookieはHttpOnly・Secure・SameSiteを適切に設定し、トークンをlocalStorageへ複写しない。期限・Cookie・ログアウト連携は採用版で実装確認が必要。

### 11.5 操作権限

以下の権限名は設計上の識別子。管理者は全操作権限を持つが、業務条件を省略できない。

| 対象 | スタッフの更新権限案 | 初期状態 |
| --- | --- | --- |
| 予約 | `reservation.create` / `update` / `cancel` | すべて不許可 |
| 店舗都合の期限後操作 | `reservation.exception`を通常の変更・取消権限に追加して要求。理由必須 | 不許可 |
| 施術進行 | `reservation.start` / `complete` | 不許可 |
| メニュー・オプション・部屋・施術者 | 対象ごとの`create` / `update` / `disable` | すべて不許可 |
| 営業日・営業時間、休憩 | `businessSetting.manage`、`therapistBreak.manage`（訂正・予定取消を含む） | 不許可 |
| スタッフ作成 | `staff.create` | 不許可 |
| 会員 | `member.forceWithdraw` / `delete` / `restore` | すべて不許可 |
| 変更案内・対応 | `notice.send` / `notice.updateResponse` | すべて不許可 |
| スタッフ権限の付与・解除 | 管理者専用。スタッフへ付与する権限キーを作らない | 委譲不可 |

表の省略表記は対象の接頭辞を共有する（例：予約の`update`は`reservation.update`）。未定義の操作は不許可。スタッフの無効化・認証情報管理も初期案では管理者専用とする。

閲覧は有効な店舗利用者の共通権限とし、予約一覧・履歴・予約に必要な顧客情報、マスタ、要調整一覧を対象とする。パスワードハッシュ・トークン・秘密情報は対象外。スタッフ権限編集画面は管理者専用。権限表を閲覧許可のない情報まで公開する根拠にしない。

会員には店舗権限を付与しない。自分の予約・会員情報への操作は、会員状態と所有者一致で認可する。代理予約は店舗側の登録権限に加えて対象会員の予約可否を確認する。

### 11.6 サーバー側の処理順序と競合

1. 公開閲覧以外では認証セッションとDBの失効状態を確認する。
2. 主体種別と最新の会員／スタッフ状態を確認する。
3. 会員操作では所有者を、店舗操作では最新の操作別権限を確認する。
4. 入力・受付期限・会員状態・予約状態・空き等の業務条件を検証する。
5. 更新処理はトランザクション内でも認可状態を再確認し、保存・監査記録を確定する。

権限解除と予約更新が競合するときは、両方を第8.6節の同じ排他制御に参加させる。解除が先に確定すれば更新を拒否し、更新が先に確定した場合はその操作を過去に遡って取消しない。セッション失効・スタッフ無効化も保護された更新との順序を揃える。具体的なロックはTask 4.2で検証する。

認可はRoute Handler・Server Actionから呼ぶ共通サービスで行い、画面・レイアウトやProxyだけに依存しない。更新はGETで実行せず、認証ライブラリの保護に加えて独自の更新入口でもCSRF対策を適用する。ログイン後の戻り先は同一サイト内の許可したパスに限定する。

未認証・失効はログインへ案内（APIは401）、権限不足は403、自分以外の会員予約は存在を開示しない404を基本案とする。DB障害は503等の一時エラーとし、認証失敗と混同しない。

| メールは異なり、退会済み会員と姓・名の照合キーが一致 | メール確認後も審査待ち。店舗が同姓同名の別人と確認した場合だけ入会を許可 |
| メールは異なり、有効会員と氏名だけ一致 | 同姓同名だけで重複と断定せず、通常のメール確認へ進む |
| 一致するメールも退会者の氏名もない | メール確認へ進む。ただし同一人物を完全に識別できたとは扱わない |

氏名一致の審査は管理者専用とする案。別人と判断した根拠・操作者・日時を記録し、同一人物と判断した場合は新規入会を認めない。既存会員を復旧する操作とは分離する。曖昧な場合は審査待ちを維持し、予約・会員ログインを許可しない。この審査画面・状態は採用後にStory 3.3／6.3へ追加する。

### 12.2 正規化と一意性

- メールは初期リリースではASCIIの通常のメール形式を対象とする案。非ASCIIのローカル部・国際化ドメインの直接入力・引用形式は未対応として入力エラーにする。最大254文字と形式検証を行う。
- 前後空白除去後の値を配送用として保持し、ASCII小文字化した値を照合キーにする。ローカル部も大文字小文字を区別しないことを本アプリのアカウント規則とする。
- `+tag`やドットは削除しない。メール事業者固有の別名規則によって別アドレスを統合しない。
- Memberのメール照合キーへDB一意制約を置く。メール未確認・審査待ち・退会済みも対象とする。同時登録は制約で1件だけ作成する。
- スタッフはStaffAccount内で同様のメール一意性を持つ。会員とは別の主体であり、自動連携しない。
- 氏名は表示値を保持し、照合キーだけNFKC正規化・前後空白除去・連続空白の半角スペース1文字化・ASCII英字の小文字化を行う案。姓と名を別々に比較し、結合による区切り消失を避ける。
- 異体字・読み・中黒・ハイフンを推測変換しない。氏名の一致は審査候補であり、本人同一性の証明ではない。氏名へ一意制約は置かない。

登録受付とメール確認完了時の両方で最新の退会者氏名を照合する。審査承認時にも再検証し、退会処理との競合は共通の排他制御で順序を揃える。

### 12.3 登録途中・重複登録

新規登録はメール未確認の会員と確認トークン・送信要求を同一トランザクションで作成する。メール確認前の予約・通常ログインは拒否する。

既存メールへの再登録で、保存済みの氏名・パスワードを未認証要求から上書きしない。未確認の場合は専用の再送手続きを案内し、確認後に必要ならパスワード再設定を行う。第三者が先に未確認登録した場合も、メール確認だけでその第三者の既知のパスワードが使える状態にしないため、**入会確認完了のPOSTでパスワードを再入力して設定する**案とする。初回登録時のハッシュを置き換え、確認前に発行されたセッション・再設定トークンは利用できない状態を保つ。

重複の有無によらず、有効な形式の受付には同じ案内を返す。形式エラーとIP制限以外では会員状態を応答に含めない。確認完了・審査承認後も自動ログインせず通常ログインへ案内する。

### 12.4 パスワード保存

15〜128 Unicodeコードポイント、無加工という採用済み仕様を維持する。UTF-8へ変換して全体をハッシュし、先頭だけを使わない。

会員・スタッフにはArgon2idを採用する案。初期候補はメモリ19 MiB・反復2・並列度1とし、利用者ごとにランダムソルトを生成するライブラリを使用する。これは[OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)の推奨構成に基づく。パラメータ・ソルトを含むハッシュ文字列だけをDBへ保存し、照合にはライブラリの検証機能を使う。

具体的パッケージと版はNode.js実行環境・Vercelのビルド、128文字の非ASCII入力、メモリ・処理時間を検証して固定する。ログイン時に保存形式が旧設定なら、照合成功後に再ハッシュする。存在しないアカウントにも同等のダミーハッシュ検証を行い、応答差を測定する。ハッシュ実行前に試行制限を適用する。

管理者は前章どおり環境変数で資格情報を管理し、DBにパスワードを保存しない。管理者のパスワード忘れは公開再設定APIの対象外とし、環境変数と認証版を運用手順で更新する。スタッフのメール再設定はスタッフ用入口で有効スタッフを対象にする。

### 12.5 トークンの用途・発行・保存

| 用途 | 有効期限 | 消費時の条件・結果 |
| --- | --- | --- |
| 入会確認 | 発行から24時間 | 未確認会員、メール一致。確認日時・新しいパスワードを保存し、必要なら氏名審査待ちへ |
| 復旧確認 | 発行から24時間 | 権限者が開始した復旧待ち。確認後に既存会員を有効化、取消済み予約は復活しない |
| パスワード再設定 | 発行から1時間 | メール確認済み・有効な会員または有効スタッフ。新ハッシュ保存と認証版更新 |

- 暗号学的乱数32バイトからURL安全なトークンを作る案。AuthTokenにはSHA-256ダイジェスト、主体種別・ID、用途、メール照合キー、認証版、発行・期限・使用・失効日時を保存する。推測困難なランダムトークン用のダイジェストとパスワード用ハッシュは使い分ける。
- 期限は`現在時刻 < expiresAt`で有効とし、期限ちょうどは拒否する。通常予約締切の境界とは異なる。
- URLは設定済みのアプリの正規オリジンから生成し、受信したHostヘッダーを信用しない。用途違い・主体違い・メール変更後・認証版不一致は拒否する。
- GETは確認画面の表示だけで、メール確認・復旧・再設定はPOSTで確定する。メールのリンクスキャナーが開いただけでは消費しない。
- トークンを含む画面は外部解析・外部リソースを載せず、キャッシュ禁止・Referrer-Policyを適用する。URLクエリをアクセスログ・監視へ残さない構成も確認する。

乱数・単回使用・安全な保存・共通応答は[OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)を参照した。具体的な32バイト・期限境界・状態条件は本アプリの設計案。

### 12.6 単回使用と競合

トークンの条件付き消費、会員状態またはパスワード更新、認証版更新、同用途の残りトークン失効を同一トランザクションで行う。未使用・未失効・期限内・対象状態一致を満たした1件だけを消費し、更新件数0なら無効として拒否する。

パスワードのハッシュ計算はトランザクション開始前に行ってよいが、確定時にトークンと会員状態を再検証する。入力不正や途中失敗ではトークンを消費しない。二重POSTは一方だけ成功する。退会・再送・復旧取消・別の再設定と競合した場合も、共通の排他制御で順序を揃える。

再設定成功時は既存セッションを失効させ、通常ログインへ案内する。退会済み会員のパスワード再設定で会員を有効化しない。復旧確認リンクも、復旧開始後に再び退会処理が行われた場合は無効とする。

### 12.7 利用者再送とシステム再試行

| 種類 | トークン | 送信要求 |
| --- | --- | --- |
| 利用者の再送 | 同用途の旧トークンを失効、新規発行 | 新しい要求を作成 |
| SMTPの一時障害 | 同じトークン、期限は延長しない | 同じ要求で初回失敗から1・5・30分後、最大3回再試行 |
| 期限切れ・使用済み・失効済み | 発行し直さない | 再試行停止。新たな利用者操作が必要 |

AuthTokenには原文を保存しない一方、同じトークンでSMTP再試行するため、EmailDeliveryに必要な送信ペイロードを専用鍵で認証付き暗号化して保持する案。鍵はDBと分離してサーバー環境変数で管理し、復号は送信処理だけで行う。専用鍵をAUTH_SECRETと共用しない。

送信受付済み・失効・期限切れ・恒久失敗等で再試行不要になったら暗号化ペイロードを削除し、状態・試行履歴だけを残す。結果不明時の扱いはREADMEに従い、期限を超えて秘密を保持しない。送信直前もトークン状態を確認するが、既にSMTPへ渡ったメールは回収できないため、届いた古いリンクを確実に拒否する。

トークン発行・旧トークン失効・送信待ち登録は一括保存する。SMTP通信はトランザクション外で実行する。

### 12.8 再送・ログイン試行の制限

READMEのメール単位の制限を維持し、IP・ログインの値は次の案とする。カウンタは全インスタンスで共有し、原子的に判定・加算する。プロセスメモリだけに保存しない。

| 操作 | キー・上限案 | 超過時 |
| --- | --- | --- |
| 入会・復旧・再設定メール要求 | 正規化メール単位で用途横断、60秒間隔かつ直近1時間5回。初回も含む | 共通受付文言を返すが発行・送信しない |
| 同メール要求のIP制限 | 信頼できる接続元IP単位で直近1時間20回、全用途合算 | 429と再試行可能時刻を返す |
| ログイン | 主体種別＋正規化メールで直近15分5回、IPで直近15分30回 | 429。時間窓が過ぎれば再試行可、永久ロックしない |
| トークン確定要求 | IPで直近15分30回 | 429。トークン自体の状態は変更しない |

- メールの登録有無によらず同じキーで数える。ログインは成功・失敗を含む試行数とし、成功でカウンタを消さない。
- 時間窓は`(現在時刻−窓幅, 現在時刻]`。60秒ちょうどなら間隔条件を満たすが、1時間の件数条件も満たす必要がある。
- 制限判定で拒否した再送は旧トークンを失効させない。複数同時要求で上限を超えて発行しない。
- 利用者再送カウンタにSMTP再試行を加算しない。店舗による復旧開始にもメール送信量の上限を適用する。
- IPはデプロイ先の信頼できるプロキシから取得し、利用者が自由に送った転送ヘッダーをそのまま使わない。IPv6の集約方法・保持期間は運用設計で確定する。
- 共有制限基盤が使えない場合は一時エラーとし、無制限に認証・送信へ進まない。メールキーは専用鍵によるHMAC等でカウンタに保持し、平文メールの技術ログ出力を避ける。

### 12.9 検証例

| ID | 条件 | 期待結果 |
| --- | --- | --- |
| IDENTITY-01 | 大文字小文字・前後空白だけ異なる既存メール | 同一キー、新規登録不可 |
| IDENTITY-02 | 退会済みメールで氏名変更 | 新規登録不可、既存会員の復旧のみ |
| IDENTITY-03 | 別メールで退会者氏名一致 | メール確認後も審査待ち、予約不可 |
| IDENTITY-04 | 審査で別人／同一人物と判定 | 別人のみ承認。同一人物は新規入会不可、理由記録 |
| IDENTITY-05 | plusタグやドットの有無 | 勝手に統合しない |
| IDENTITY-06 | 同じメールの同時登録 | DBには1会員だけ。応答に存在情報を漏らさない |
| IDENTITY-07 | 未認証の再登録で既存パスワードを指定 | 既存値は上書きされない |
| IDENTITY-08 | 第三者が作った未確認登録をメール所有者が確認 | 確認POSTで所有者が新パスワードを設定。第三者の旧パスワードは使えない |
| TOKEN-01 | 入会・復旧24時間、再設定1時間の直前／ちょうど | 直前のみ有効、ちょうどは失効 |
| TOKEN-02 | 同トークンで同時POST | 成功は1件、残りは拒否 |
| TOKEN-03 | 確定処理の途中でDB失敗 | トークン消費と状態更新をともに取り消す |
| TOKEN-04 | 再送後の旧リンク、用途違いのリンク | 拒否 |
| TOKEN-05 | リンクのGET・メールスキャナー | 表示のみ、状態を変更しない |
| TOKEN-06 | 再設定と退会が同時実行 | 有効条件を再確認し、退会者が有効化されない |
| TOKEN-07 | 非ASCII128文字・129文字のパスワード | 前者は全体を処理、後者は入力拒否。切り捨てなし |
| TOKEN-08 | SMTP再試行・期限切れ | 同じトークンを使用、期限切れ後は送らない |
| LIMIT-01 | 前回発行から59秒／60秒 | 59秒は拒否、60秒は時間窓の件数も検証 |
| LIMIT-02 | 同メールの直近1時間5回目／6回目 | 5回目まで許可、6回目は送信なし。用途変更でも回避不可 |
| LIMIT-03 | 制限中に再送要求 | 旧トークンは引き続き期限まで有効 |
| LIMIT-04 | 複数インスタンスで同時要求 | 共有カウンタにより上限を超えない |
