# Epic 5 詳細設計：会員Web予約

## 1. Story 5.1 の範囲と画面遷移

`/book` は公開画面。メニュー選択、複数オプション選択、税込合計、日付、空き時刻まで非会員も利用できる。「予約内容を確認」時に `/api/member/me` で予約可能な本人を確認する。認証が必要なら `/login?next=%2Fbook` と `/register?next=%2Fbook` を案内する。ログイン成功後は `next` が厳密に `/book` のときだけそこへ戻し、それ以外の会員ログインは `/account` とする。登録はメール確認が必要なので、登録画面・メール確認画面のログインリンクから予約へ進める。

```
公開選択 → 空き検索 → 時刻・備考 → 会員確認 → 送信前確認 → POST /api/reservations → 完了
                                  └ 401 → ログイン → /book → 空き再検索
```

選択したメニュー・オプション・日付・備考だけを `sessionStorage` に一時保存する。会員情報・予約キー・空き時刻は保存しない。ログインから戻った後、空きは再検索し時刻を選び直す。予約完了時に一時保存を削除する。

## 2. Task 5.1.1：公開メニューと税込合計

公開 `GET /api/catalog` は有効な Treatment/Option の ID・名称・時間・税込料金だけを作成順で返す。失敗は503、全応答 `Cache-Control: no-store`。画面ではメニューを1件、オプションを複数選択する。各金額は既に税込なので加算だけを行い、時間1〜1,380分・税込料金0〜1,000,000円という既存のサーバー制約を超えた選択は検索不可とする。検索結果のサーバー算出合計を送信前確認と保存APIの `quote` に使用し、保存側はDBから再計算する。

## 3. Task 5.1.2：公開空き検索

`/book`には翌日から30日先までをカバーする月カレンダーを表示する（既存の受付ルールに合わせ、暦月の1ヶ月後ではなく30日先を上限とする）。月をまたぐ場合は該当する月をすべて表示し、PCでは複数月を2列、スマートフォンでは縦に並べる。

メニュー・オプション選択後、公開`GET /api/availability/calendar`へメニューIDと各オプションIDを送る。サーバーのAsia/Tokyo日付を基準に翌日〜30日先の空き開始時刻数・受付期間外フラグを返す。各日付の判定は既存の`findAvailability`を共有し、DB同時処理を3日に制限する。既存の空き計算・営業時間・受付期限・資源条件を変更しない。取得中・メニュー未選択・空きなし・受付期間外は日付を無効化しグレー表示する。取得失敗は空きなしとして扱わず、再取得を案内する。全応答は`no-store`。

空きのある日付をクリックするとshadcn/ui（Radix）のDialogを開き、`GET /api/availability`へ日付・メニューID・各オプションIDを送って最新の空き時刻を取得する。時刻ボタンを選ぶと日付・時刻・サーバー算出合計を親フォームに反映して閉じる。キャンセル時は直前の確定した日時を維持する。Escape・閉じるボタン・背景クリックで閉じ、フォーカスを選択元の日付へ戻す。日付が無効化された場合は見出しに戻す。最後の枠が埋まっていた場合は案内し、その日付を無効化する。

メニュー・オプション変更時は選択済み日時を解除し、日別の空きを取り直す。旧リクエストはAbortControllerで中断し、選択キーの異なる結果を表示しない。競合時の既存の日別再検索後もカレンダーを再取得する。「空きを更新」で日別状況を再取得できる。保存時の最終空き判定は既存の予約トランザクションを維持する。日時表示はAsia/Tokyo。


## 4. Task 5.1.3：本人情報・検証・確認・完了

`GET /api/member/me` は `requireBookableMember` で毎回本人の予約可否を確認し、氏名・メール・電話番号だけを返す。401はログイン、403は会員状態の確認、503は再試行を表示する。備考は任意で1,000コードポイント以内。画面のセクションは「3. 備考」、入力ラベルは「ご要望など（任意・1,000文字以内）」とする。画面で事前検証し、保存APIも再検証する。送信前確認には会員連絡先、メニュー・オプション、日時、合計、備考を表示する。201応答の予約IDを完了画面に表示する。会員IDはクライアントから送らず、保存APIがセッションから決定する。

## 5. Task 5.1.4：競合と二重送信

確認した内容に対してUUIDの `requestKey` を1つ生成し、送信中はボタンを無効化するとともに同期的なロックで多重発火を止める。通信失敗や結果不明では同じキー・同じ内容で再試行し、既存APIの再送結果を受け取る。選択や備考を変えた場合は新しいキーを使う。409なら確認と時刻を解除してカタログと空きを再取得する。`SelectionChanged` は料金・内容の再確認、それ以外の409は時刻の再選択を案内する。保存時の空き・料金・会員・受付期限・競合制約の最終判断は既存の予約トランザクションが行う。

## 6. Task 5.1.5：案内とセッション期限切れ

公開画面から入会・ログインへ遷移できる。会員情報取得または保存時に401になれば確認状態を解除し、ログイン後の復帰を案内する。403は会員状態による不可として区別する。ログイン成功の復帰先は固定の `/book` だけを許し、任意URLを受け付けない。復帰した選択内容で改めて空きと会員状態を確認する。

## 8. Story 5.2：マイページからの予約確認・キャンセル

### Task 5.2.1：本人限定の一覧・詳細

`/account` はログイン中の会員に紐付く予約を一覧にし、`/account/reservations/{id}` に予約時点の日時、施術メニュー・オプション、料金、部屋、担当、氏名・連絡先、備考、状態を表示する。日時は `Asia/Tokyo` の24時間表記でゼロ埋めする。`GET /api/reservations` と `GET /api/reservations/{id}` も同じ取得処理を使う。会員IDはクエリ文字列や画面入力では受けず、`requireBookableMember` による検証済みセッションから得る。一覧は `where: { memberId }`、詳細は `where: { id, memberId }` でDB検索する。他人のIDと不正形式のIDは404に統一し、詳細の存在や個人情報を漏らさない。応答は `no-store`。ログイン切れは401、予約不可の会員状態は403、DB取得失敗は503。

### Task 5.2.2：期限、確認、取消、結果

通常キャンセル期限は予約日前の直近営業日の閉店時刻。保存処理と表示処理が `cancellationDeadline` を共有し、休業日の繰り上げ、対象日に有効な営業時間、期限時刻ちょうどの許可を同じ計算にする。詳細画面は予約状態が `CONFIRMED` で期限内のときだけ取消確認を表示する。確認画面には期限と取消後に元へ戻せないことを示す。確定時は既存 `DELETE /api/reservations/{id}` へUUIDの `requestKey` と表示版 `expectedVersion` を送る。クライアント側の同期ロックとボタン無効化で二重クリックを抑止し、結果不明の再試行は同じキーを使う。保存APIが本人・状態・版・期限をトランザクションで再判定する。成功後は結果を表示し画面を更新する。期限超過、版衝突、セッション切れ、認可失敗は個別に案内する。

### Task 5.2.3：認可・改ざん・再操作の検証

## 9. Story 5.3：会員本人による退会

### Task 5.3.1：理由と対象予約の確認

マイページから `/account/withdraw` へ進む。ログイン中かつ予約可能な本人だけが表示できる。理由は選択肢「利用予定がなくなった」「サービスが合わなかった」または「その他」の自由記述を必須とし、自由記述は空白のみ・1,000コードポイント超を拒否する。`GET /api/member/withdraw/preview` は対象会員をセッションから確定し、会員版、確定予約のID・日時・メニュー、施術中・完了済み・取消済みの件数を `no-store` で返す。確認画面を開く際に再取得し、対象となる全 `CONFIRMED` 予約を表示する。過去日時でも状態が `CONFIRMED` なら退会時に取り消す。施術中予約と占有枠、完了・取消済みの履歴、会員情報を保持すること、全セッションが失効し新規予約ができなくなることを明示する。

確認時の会員版と確定予約のID・版の集合からSHA-256の `reviewToken` を生成する。これは本人認可の代替ではなく、表示後に対象予約が変化したことを検出するための値。保存APIは既存呼び出しとの互換性のためトークン省略も受け付けるが、画面からの送信には必須とする。トランザクションが会員と予約をロックした後に値を照合し、相違時は409 `ReservationSetChanged` として何も変更せず、画面は最新の対象予約を再取得する。理由・版・対象予約を見直してから新しい `requestKey` で確定する。

### Task 5.3.2：退会実行、セッション終了、結果

確定時は `POST /api/member/withdraw` に `requestKey`、`expectedVersion`、`reviewToken`、`reason` を送り、会員IDは送らない。既存の `withdrawSelf` が署名付きセッションをトランザクション内で再確認し、会員を `WITHDRAWN`・`isDeleted=true` に更新する。確定予約を期限後も自動取消して枠を解放し、施術中・完了・取消済み予約と個人情報・履歴を維持する。同じトランザクションで全 `AppSession` を失効する。成功応答では会員セッションCookieも有効期限0で削除し、画面に実際の取消件数と完了結果を表示する。以後の古いCookieによる予約登録・会員画面閲覧は拒否する。

送信中はボタンを無効化し、同じ画面からの二重送信を同期的に防ぐ。通信結果が不明な場合は同じキーでの再試行を案内するが、DBでは退会成功後にセッションが失効するため再送が401になる場合がある。401だけで成功と断定せず、結果不明の案内を表示する。409は会員版または対象予約の変化として確認へ戻す。退会前の理由空白、未ログイン、対象変更をサーバーでも拒否する。
